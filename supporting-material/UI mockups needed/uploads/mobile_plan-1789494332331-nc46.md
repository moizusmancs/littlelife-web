# LittleLife Mobile — Design Plan

**Standalone document.** Everything needed to design every screen and every component inside it
is contained here — no need to cross-reference `MOBILE_IMPLEMENTATION_PLAN.md` or the backend
roadmap to use this. Where app structure needs restating for context (the five-tab shell, what a
screen is *for*), it's restated briefly rather than assumed.

**What this app is:** LittleLife — a citizen-facing flood safety app for Pakistan. People open it
in two very different mental states: calm, everyday use (checking local reports, browsing
resources, building community trust) and acute crisis use (an active flood alert, reporting a
hazard in the rain, finding the nearest shelter). The design has to serve both without one
undermining the other — friendly and warm in the calm state, unambiguous and fast in the crisis
state. That tension is the single biggest driver of the decisions below, especially the color
system (§1.2) and the deliberate split between "brand chrome" and "system/severity color" (§1.2.4).

**How to use this document:** §1–2 are the design system (tokens + primitives) — build these
first, they're referenced by every screen after. §3 defines reusable screen *patterns* so the
50-odd screens in §4 don't each re-explain the same list/detail/form skeleton — each screen entry
names its pattern and then only describes what's specific to it. §5 covers global/system UI that
lives outside any one screen. §6–7 are handoff notes.

## 1. Brand & visual identity

### 1.1 Brand personality

Warm, human, calm-under-pressure. Not clinical/government (the SDS's own problem statement is
partly that NDMA's existing tooling feels exactly that way), not saccharine-cute either — this is
still an app someone opens while standing in floodwater. Peach/pink reads as approachable and
community-oriented (this is a mutual-aid and neighborhood-trust product as much as a hazard-data
product); it is *not* used anywhere severity/status needs to be unambiguous — that's a hard rule,
not a suggestion (§1.2.4).

### 1.2 Color system

#### 1.2.1 Primary — Rose (peach-pink family, main brand/action color)

| Token | Hex | Usage |
|---|---|---|
| `primary.50` | `#FFF0F4` | Tinted backgrounds behind primary content (e.g. selected chip fill) |
| `primary.100` | `#FFDCE6` | Hover/pressed tint on light surfaces, subtle section backgrounds |
| `primary.200` | `#FFB8CD` | Disabled-but-visible primary elements, decorative accents |
| `primary.300` | `#FF8FAF` | Secondary emphasis text on light bg, illustration accents |
| `primary.400` | `#FA6C97` | Hover state of primary buttons |
| **`primary.500`** | **`#F2477D`** | **Base primary — default button fill, active tab icon, links, brand marks, progress bars, primary FAB** |
| `primary.600` | `#DB2E68` | Pressed/active state of primary buttons |
| `primary.700` | `#B81F55` | Text-on-`primary.50` (passes AA on light tint backgrounds) |
| `primary.800` | `#8F1745` | Rarely used — deep accent for dark-mode primary text |
| `primary.900` | `#661038` | Rarely used — darkest brand accent |

`primary.500` on white text: contrast ratio ≈ 4.6:1 — passes WCAG AA for normal text and UI
components; do not go lighter than `primary.500` for filled-button backgrounds carrying white text.

#### 1.2.2 Secondary — Peach (brand accent, pairs with Rose for gradients/illustration)

| Token | Hex | Usage |
|---|---|---|
| `peach.50` | `#FFF6EF` | Card backgrounds for "calm state" content (Home hero, onboarding) |
| `peach.100` | `#FFE8D6` | Illustration fills, empty-state backgrounds |
| `peach.200` | `#FFCEA8` | Decorative accents |
| `peach.300` | `#FFB183` | Secondary accent icons |
| **`peach.400`** | **`#FF9563`** | **Base peach — gradient partner to `primary.500` (brand gradient = `primary.500 → peach.400`, 135°), secondary button fill on dark surfaces** |
| `peach.500` | `#F97C4D` | Hover of peach elements |
| `peach.600` | `#E0632F` | Pressed state |

The brand gradient (`primary.500` → `peach.400`, top-left to bottom-right) is reserved for: app
icon, splash screen, onboarding backgrounds, the primary CTA button on Login/Register, and the
Home screen's greeting header background. It is a *decorative/hero* device — never used as a
background behind data that needs to stay legible in bright outdoor light (no gradient behind map
overlays, hazard cards, or alert content).

#### 1.2.3 Ink — the contrast anchor (per brief: "primary and rest contrast color")

A deep, cool-adjacent near-black with a faint plum undertone, so it harmonizes with Rose/Peach
instead of reading as a mismatched generic gray. This is the "rest contrast color" — it carries
all body text, all dark surfaces, outlined/secondary buttons, and dark-mode chrome.

| Token | Hex | Usage |
|---|---|---|
| `ink.900` | `#221019` | Primary text, headings, icons-on-light |
| `ink.700` | `#4A2E3C` | Secondary text |
| `ink.500` | `#7A5A68` | Muted/tertiary text, placeholder text, inactive tab labels |
| `ink.300` | `#B79AA6` | Disabled text, dividers on colored surfaces |
| `ink.100` | `#EDE3E7` | Hairline borders, dividers on white |
| `ink.900` (as surface) | `#221019` | Dark-mode app background; dark-mode nav bar |

#### 1.2.4 Semantic / status colors — deliberately outside the pink/peach family

**Hard rule, carried forward from the product's own safety requirements: brand color (Rose/Peach)
is never used to encode hazard severity, verification status, or system state.** A citizen glancing
at a red badge must never wonder "is that a brand accent or is that real danger." Status colors
are chosen from entirely different hue families so there is zero perceptual overlap with the
brand palette, even for color-blind users (verified against a deuteranopia/protanopia simulation
pass during handoff, §7).

| Token | Hex | Meaning | Background tint |
|---|---|---|---|
| `status.safe` | `#2E9E5B` (green) | Low risk, resolved, "I'm Safe," open/available | `#E3F6EA` |
| `status.caution` | `#E0A100` (amber) | Medium risk, pending/unverified, general advisory | `#FFF4D9` |
| `status.high` | `#F0740B` (true, saturated orange — deliberately more saturated/red-shifted than `peach.400` so it never gets mistaken for a brand accent) | High risk, warning-level alert, urgent (non-critical) | `#FFE9D6` |
| `status.critical` | `#D42E2E` (red) | Critical emergency alert, active life-risk hazard, "I Need Help" | `#FDE4E4` |
| `status.trust` | `#1F7A8C` (teal-blue) | Credibility score, "Verified" badge, official NGO/admin content | `#E1F1F4` |
| `status.info` | `#3A5FCD` (blue) | Neutral informational banners, offline/connectivity notices | `#E7ECFB` |

`status.critical` is additionally reserved: it must never be reused for a generic destructive
action (e.g., "Delete account," "Cancel request"). Generic destructive actions use `ink.900` text
on a `status.critical`-*bordered*, white-filled button (outline style) — visually calmer than a
solid-red button, so solid `status.critical` fill is a signal that means "this is happening right
now, act on it," not "this is a delete confirmation."

| Medical | `#7C4DFF` (violet) | Stands apart from everything else on a map |
| Infrastructure / Utility | `#5C6B7A` (slate) | |
| Cloudburst | `#4F8FE0` (lighter blue, distinguishable from Flooding) | |

| Token | Hex | Usage |
|---|---|---|

| `surface.raised` | `#FFFFFF` | Cards, sheets, modals (pure white so raised content pops off the warm base) |
| `surface.sunken` | `#FDEFEA` | Input field backgrounds, secondary card fill |

#### 1.2.7 Dark mode (secondary priority — see §1.7)

| Token (light → dark) | Dark value |
|---|---|

### 1.3 Typography

Two type stacks, chosen because **Latin display/UI fonts do not cover Urdu script** — a single
font choice would silently fall back to the OS default for Urdu users and break the brand voice
exactly for the audience the app most needs to reach clearly.

| Locale | Headings/Display | Body/UI |
|---|---|---|
| English (`en`) | **Manrope** (600/700) — geometric, warm, rounded terminals; friendly without being juvenile | **Inter** (400/500/600) — excellent legibility at small sizes, wide language support as a fallback |
| Urdu (`ur`) | **Noto Naskh Urdu** or **Noto Sans Arabic** (600) | **Noto Sans Arabic** (400/500) | *Not* Noto Nastaliq Urdu for UI body text — Nastaliq is visually beautiful but its diagonal flow and variable line-height break in dynamically-sized UI containers (form fields, chat bubbles, badges); reserve true Nastaliq for a one-off splash/marketing use if desired, never for interactive UI. |

Type scale (applies to both stacks, sizes in `sp`/`pt`):

| Token | Size | Weight | Line height | Usage |
|---|---|---|---|---|
| `display` | 32 | 700 | 40 | Onboarding hero headlines only |
| `h1` | 24 | 700 | 30 | Screen titles |
| `h2` | 20 | 600 | 26 | Section headers, card titles |
| `h3` | 17 | 600 | 22 | List item titles, sub-section headers |
| `body.lg` | 16 | 400 | 24 | Primary body copy, form input text |
| `body.md` | 14 | 400 | 20 | Secondary body copy, card descriptions |
| `body.sm` | 12 | 500 | 16 | Captions, timestamps, helper text |
| `label` | 13 | 600 | 16 | Button labels, tab labels, chip text — slightly letter-spaced (+0.2) |
| `overline` | 11 | 700 | 14 | ALL-CAPS section eyebrows ("QUICK ACTIONS"), +0.8 letter-spacing |

Minimum body text size 14 (`body.md`) per accessibility floor; nothing in the app goes below
`body.sm` (12) except a single micro-timestamp use case.

### 1.4 Spacing & layout grid

4pt base unit. Tokens: `space.1`=4, `space.2`=8, `space.3`=12, `space.4`=16, `space.5`=20,
`space.6`=24, `space.8`=32, `space.10`=40, `space.12`=48.

- Screen horizontal margin: `space.4` (16) on phones, `space.6` (24) on tablets.
- Card internal padding: `space.4` (16).
- Vertical rhythm between stacked sections on a screen: `space.6` (24).
- Vertical rhythm between elements inside a card: `space.3` (12).

### 1.5 Radius & elevation

Soft, rounded aesthetic — matches the warm brand, and rounded corners at this radius read as
"friendly/community" rather than "institutional," which is the intended contrast to NDMA-style
tooling.

| Token | Value | Usage |
|---|---|---|
| `radius.sm` | 8 | Chips, badges, input fields |
| `radius.md` | 12 | Cards, buttons |
| `radius.lg` | 20 | Bottom sheets (top corners), modals |
| `radius.full` | 999 | Pills (segmented controls, FAB, avatar) |

Elevation uses warm-tinted shadows (`rgba(34,16,25,0.08)` — derived from `ink.900`, not pure
black) so shadows feel consistent with the palette rather than gray/cold.

| Token | Shadow |
|---|---|
| `elevation.0` | none (flat surfaces) |
| `elevation.1` | `0 1px 3px rgba(34,16,25,0.08)` — cards at rest |
| `elevation.2` | `0 4px 12px rgba(34,16,25,0.12)` — raised cards, dropdowns |
| `elevation.3` | `0 8px 24px rgba(34,16,25,0.16)` — modals, bottom sheets, FAB |

### 1.6 Iconography

**Phosphor Icons**, two weight variants used deliberately for different contexts:
- **Duotone/Fill weight**, tinted with `primary.500`/`peach.400` — used in calm-state chrome (Home
  quick actions, Profile menu items, onboarding) where warmth matters more than split-second
  legibility.
- **Bold/Regular stroke weight**, tinted with the relevant status color — used for anything
  severity/status-bearing (map markers, severity badges, alert icons) where instant, unambiguous
  recognition matters more than brand warmth. This split is the visual expression of the same
  calm-vs-crisis principle from §1.1.

Map markers use custom pin shapes (not generic Phosphor map-pin) colored by `status.*`/category
tokens, per §1.2.4/§1.2.5 — detailed in the Map screen spec (§4.3).

### 1.7 Motion

150–250ms ease-out for standard transitions (screen pushes, sheet presentation, button press
feedback). Nothing in the app uses a transition longer than 300ms — this is a warm brand, not a
slow one; an emergency-adjacent app that feels sluggish erodes trust immediately. Critical alert
takeover (§4.11) uses a hard, fast presentation (150ms, no bounce/spring easing) — deliberately
less "designed" and more abrupt than everything else, so its arrival itself communicates urgency.

### 1.8 Accessibility baseline

- Minimum touch target 44×44pt everywhere (buttons, list items, map controls).
- All text/background pairs checked to WCAG AA (4.5:1 body text, 3:1 large text/icons) — flagged
  per-component below wherever a combination needs care (`primary.500` on white, `status.caution`
  needs `ink.900` text not white, etc.).
- RTL: full mirroring for Urdu — not just text alignment but icon direction (back-chevrons,
  progress-forward icons), covered per-component in §2.
- Dark mode is a secondary pass, not the primary design surface — severity color legibility in
  bright outdoor daylight is prioritized over dark-mode aesthetics (per SDS UI-7's own outdoor-
  visibility requirement); build light mode complete first.

## 2. Core components (design system primitives)

### 2.1 Buttons

| Variant | Fill | Text | Use |
|---|---|---|---|
| Primary | `primary.500` solid, `primary.600` pressed | white | Main CTA per screen — one per screen max |
| Secondary | `surface.raised` with 1.5px `primary.500` border | `primary.700` | Secondary actions alongside a primary button |
| Peach (accent) | `peach.400` solid | `ink.900` (not white — peach is too light for AA with white text) | Used sparingly for a second, lower-priority CTA on hero/onboarding screens only |
| Ghost/Text | transparent | `primary.700` | Tertiary actions, "View All," links |
| Danger-outline | `surface.raised` with 1.5px `status.critical` border | `status.critical` | Destructive-but-not-emergency actions (delete account, cancel request) — outline, not solid, per §1.2.4 |
| Critical-solid | `status.critical` solid | white | Reserved exclusively for in-the-moment emergency actions: "I Need Help," alert takeover CTAs |
| Safe-solid | `status.safe` solid | white | "I'm Safe" quick-action only |

Sizes: `lg` (52pt height, `body.lg` label, full-width default), `md` (44pt, most in-context
buttons), `sm` (36pt, inline card actions like "Navigate"/"Mark Closed").

States: default / pressed (darken 10%) / disabled (`ink.300` fill or border, `ink.300` text, no
shadow) / loading (label replaced by a small spinner in the same text color, button stays same
size — no layout shift).

### 2.2 Inputs

- **Text field**: `surface.sunken` fill, `radius.sm`, `ink.900` text, `ink.500` placeholder,
  `space.3` internal padding, leading icon slot (Phosphor, `ink.500`), optional trailing icon
  (e.g. password-visibility eye toggle). Focus state: 2px `primary.500` border replacing the
  default 1px `surface.border`. Error state: 2px `status.critical` border + `body.sm` error text
  in `status.critical` beneath the field.
- **Textarea**: same as text field, min-height 96pt, character counter (`body.sm`, `ink.500`,
  bottom-right) for fields with a documented minimum (e.g. "42/20 min" pattern for incident
  descriptions).
- **OTP input**: 6 individual boxes, `radius.sm`, 48×56pt each, `space.2` gap, auto-advance focus,
  filled box gets `primary.500` border, error state shakes horizontally (150ms) and turns all
  boxes' border `status.critical`.
- **Segmented control** (Login/Register toggle, category filter tabs): pill container
  (`radius.full`, `surface.sunken` fill), selected segment gets a `primary.500` filled pill behind
  white `label` text, unselected segments show `ink.700` `label` text on transparent.
- **Toggle switch**: 51×31pt, off = `ink.300` track, on = `primary.500` track, white thumb.
- **Slider**: `primary.500` filled track, `peach.400` unfilled track, `primary.600` thumb with a
  subtle `elevation.1` shadow.
- **Dropdown/Select**: styled as a text field with a trailing chevron-down (Phosphor), opens a
  bottom sheet list on mobile (never a native inline dropdown — consistent with the sheet-based
  interaction pattern used throughout, §3).
- **Chip input** (category grid selectors on Report Incident/Request Help): square-ish cards,
  `radius.md`, icon (top, `primary.500` duotone) + `label` text (below), unselected =
  `surface.raised` with `surface.border`, selected = `primary.50` fill with 2px `primary.500`
  border and the icon recoloring to `primary.600`.

### 2.3 Cards

Base card: `surface.raised`, `radius.md`, `elevation.1`, `space.4` padding. Two variants used
throughout:
- **List card** (incident report, aid request, campaign, missing person, community post): leading
  content (thumbnail/avatar or category icon), title (`h3`), meta row (`body.sm`, `ink.500`:
  author/timestamp/location), status/severity badge top-right, optional footer row (vote counts,
  progress bar, action buttons).
- **Stat/summary card** (Home quick actions, Profile stat tiles): centered icon (duotone,
  `primary.500`), large number (`h1`), label beneath (`body.sm`, `ink.500`).

### 2.4 Badges & chips

- **Severity badge**: pill, `radius.full`, filled with the relevant `status.*` background tint,
  text in the corresponding solid `status.*` color, `label` size, small leading dot or icon.
  Single shared component (`<SeverityBadge>`) used identically on Map, Community, Home, Alerts —
  one visual definition, everywhere, per §1.2.4's consistency requirement.
- **Category chip**: pill, filled with the category color from §1.2.5 at 15% opacity as
  background, full-opacity text/icon.
- **Verified badge**: small `status.trust`-colored checkmark-in-circle (Phosphor
  `check-circle`, fill), inline after a name/title — used for verified reports, official NGO
  posts, verified essential-location status.
- **Credibility percentage chip**: pill, `status.trust` at 15% bg, `status.trust` text, e.g. "85%
  credible."

### 2.5 Navigation chrome

- **Bottom tab bar** (5 tabs: Home / Map / Community / Resources / Profile): `surface.raised`
  background, `elevation.2` (shadow above it, no border), 56pt height + safe-area inset. Each tab:
  Phosphor icon (duotone, `ink.500` inactive → `primary.500` fill + label colored `primary.500`
  when active) + `body.sm` label beneath. Active tab additionally gets a small `primary.500` dot
  indicator centered above the icon — a lightweight animated cue rather than a full pill
  background, keeping the bar visually calm.
- **Top app bar**: `surface.base` (blends into screen, no hard-edged bar) for most screens; back
  chevron (Phosphor `caret-left`, mirrors to `caret-right` under RTL) in `ink.900`, screen title
  centered (`h2`) or left-aligned depending on screen density (list screens = left-aligned title +
  right-aligned action icon; detail screens = centered title). Map and Alert Takeover screens have
  no top app bar at all — content runs edge-to-edge with floating controls instead (§4.3, §4.11).
- **FAB** (chatbot entry point, §5.2): 56×56pt circle, brand gradient fill (`primary.500` →
  `peach.400`), white chat-bubble icon, `elevation.3`, positioned bottom-right, offset above the
  tab bar, present on every `MainTabs` screen.

### 2.6 Bottom sheets & modals

Bottom sheets (`@gorhom/bottom-sheet`-style): `radius.lg` top corners only, `surface.raised`,
`elevation.3`, drag handle (4×32pt pill, `ink.300`) centered at top. Used for: Map's "Active
Hazards" summary, hazard/shelter tooltips, category dropdowns, filter panels, and any "quick
action from here" surface — sheets are the default secondary-surface pattern in this app, over
full modals, because they keep map/screen context visible underneath (important when the context
is "where am I relative to this hazard").

Full-screen modals (native-stack `presentation: 'modal'`): used only for the three multi-step
forms (Report Incident, Request Help, Report Missing Person) and Alert Takeover — content that
needs the user's full attention and a real commit/cancel decision, not a quick glance.

### 2.7 List item (generic row)

44pt minimum height, leading icon/avatar slot (24–40pt depending on context), title (`h3` or
`body.lg`) + optional subtitle (`body.sm`, `ink.500`) stacked, trailing chevron/switch/value slot.
Used for: Profile menu rows, Settings rows, Safety Group member rows, Region picker rows.

### 2.8 Avatars

Circular, `radius.full`. Default (no photo): filled `primary.100` background with initials in
`primary.700` `h3`. NGO/official accounts get a small `status.trust` badge overlapping the
bottom-right of the avatar.

### 2.9 Empty states

Centered column: illustration (soft peach/pink duotone linework, custom-illustrated — not a stock
icon blown up large, see §6 asset list), `h2` headline, `body.md` supporting line in `ink.500`,
optional primary button beneath. Every list/feed screen defines its own empty-state copy (given
per-screen in §4) rather than a generic "No data" — e.g. Community Feed empty = "No reports near
you yet — be the first to check in on your area," not "No results."

### 2.10 Loading states

Skeleton screens (shimmering `surface.sunken` blocks matching the shape of the real content) for
list/detail screens on first load; a small inline `primary.500` spinner for button-triggered
loading (submit, refresh) rather than a full-screen blocker wherever the surrounding content is
still meaningful to see.

### 2.11 Toasts, snackbars & banners

- **Toast** (transient, 3s auto-dismiss, bottom-anchored above tab bar): confirmation messages
  ("Vote recorded," "Report submitted").
- **Connectivity banner** (persistent while offline, top-anchored, `status.info` background,
  `ink.900` text): "You're offline — some actions will send once you're back online."
- **Alert banner** (Home screen, FR2.3): full-width card directly beneath the greeting header,
  `status.critical`/`status.high`/`status.caution` background tint matching the alert's actual
  severity (never brand color), icon + headline + "time remaining" + "View on Map" ghost button.

### 2.12 Media picker / uploader

Bottom sheet with two large tap targets ("Take Photo" / "Choose from Library," each a duotone
icon over a `label`), triggered from a dashed-border `radius.md` drop-zone card ("Tap to upload
photos or videos — max 5 files, 10MB each"). Uploaded items render as a horizontal scroll of
80×80pt thumbnails with a small `status.critical`-tinted remove (×) button top-right of each.

### 2.13 Progress indicators

- **Linear progress bar** (donation campaign goal, offline map download): `radius.full` track,
  `surface.sunken` background, `primary.500` fill, `body.sm` value label above-right ("PKR 10,600
  of 20,000").
- **Circular/ring progress** (credibility score, FR7.3): `primary.500` arc over `surface.sunken`
  track, percentage centered inside in `h1`.

### 2.14 Map markers & legend

- Hazard zone: filled polygon in the matching `status.*` color at 35% opacity with a 2px solid
  border at full opacity — never a hairline-only outline, needs to read at a glance while
  scrolling/panning.
- Shelter: circular pin, white fill, `status.safe` border + house icon.
- Incident report: circular pin colored by category (§1.2.5), small count badge if clustered.
- User location: standard blue dot with accuracy ring (platform-native convention — deliberately
  *not* brand-colored, so it's never confused with a hazard marker).
- A persistent legend toggle (small `?`/list icon, bottom-left of map) opens a sheet explaining
  every color/icon on screen — required given how much color-coding this screen carries.

## 3. Screen patterns (templates)

Every screen in §4 names one of these.

- **Pattern A — Auth/Form (single focus)**: centered/top-aligned content, no tab bar, no back-swipe
  distractions, one primary button pinned to the bottom safe area, minimal chrome. *(Login,
  Register, OTP, Forgot/Reset Password.)*
- **Pattern B — List/Feed**: top app bar (title + optional filter/search icon), optional segmented
  tabs beneath the app bar, scrollable list of Pattern-B-cards, pull-to-refresh, empty/loading/error
  states per §2.9–2.10, optional FAB or bottom-pinned CTA for "create new." *(Community Feed, Aid
  Requests, Campaigns, Missing Persons, Local Resources, Safety Groups list.)*
- **Pattern C — Detail**: top app bar (back + optional overflow menu), hero/media area if
  applicable, content sections stacked with `space.6` rhythm, primary action(s) pinned to bottom
  safe area (not floating mid-content). *(Incident Detail, Aid Request Detail, Campaign Detail,
  Missing Person Detail, Shelter Detail, Safety Group Detail.)*
- **Pattern D — Full-screen modal form**: presented modally (slide-up), close (×) top-left instead
  of back-chevron, `h1` form title, grouped fields with `space.6` between groups, primary submit
  button pinned to bottom safe area, always shows a save-progress/step indicator if multi-section.
  *(Report Incident, Request Help, Report Missing Person.)*
- **Pattern E — Map-based**: no top app bar, edge-to-edge map, floating search bar top-anchored
  (safe-area aware), floating layer-toggle + legend controls, bottom sheet for contextual
  summaries. *(Map, Safe Route Navigation.)*
- **Pattern F — Conversation**: top app bar (participant name/avatar + call icon if applicable),
  scrollable message list (bubbles: own messages right-aligned `primary.500` fill/white text,
  others left-aligned `surface.sunken` fill/`ink.900` text), pinned composer bar at bottom (text
  input + attachment icon + send button). *(AI Chatbot, Aid/Missing-Person threads.)*
- **Pattern G — Composed dashboard**: top greeting/header zone (often brand-gradient), multiple
  independently-loading sections stacked below with clear section headers (`overline` + `h2`),
  each section degrades independently (skeleton/empty/populated per-section, not whole-screen).
  *(Home, Profile.)*
- **Pattern H — Critical takeover**: no tab bar, no back button (dismissal is an explicit action,
  not an accidental swipe), full-bleed `status.critical`/`status.high` background tint at 8-10%
  over `surface.base`, oversized icon + headline, content sections, two large pinned action
  buttons ("I'm Safe" `status.safe` solid / "I Need Help" `status.critical` solid) side-by-side at
  the very bottom. *(Alert Takeover.)*

## 4. Screen-by-screen specifications

### 4.1 Auth & Onboarding

**Splash / Bootstrap** — Pattern A (minimal). Full-bleed brand gradient background, centered
logomark, no interactive elements; auto-transitions after token-check completes (target <800ms
perceived).

**Login / Register** — Pattern A. Top: brand gradient header block (peach→rose, `radius.lg`
bottom corners only) containing the app name/logo, curving into a white sheet below that holds the
form (matches the SDS's own approved mockup composition, Figure 2-5, re-skinned). Segmented
control (Login/Register) directly beneath the header. Login mode: email-or-phone text field,
password field (trailing eye-toggle), "Forgot Password?" ghost-link right-aligned beneath it,
primary button "Log In" (full-width, `lg`), divider with "Or continue with" (`body.sm`, `ink.500`,
`surface.border` lines either side), secondary "Continue with Google" button (`surface.raised`
outline, Google glyph leading icon). Register mode: full name, email, password, confirm password
fields stacked, inline helper text under password field ("8+ characters, upper & lower case,
number, symbol") that turns `status.safe` per-rule as each is satisfied (a small checklist, not
just a static hint), primary button "Register," legal footnote (`body.sm`, `ink.500`) beneath.
Failed-login and lockout states surface as an inline banner above the form (`status.critical` tint,
not a modal alert) — "Too many attempts — try again in 14:32."

**OTP Verification** — Pattern A. Centered envelope-check duotone illustration, `h1` "Check your
email," `body.md` "We sent a 6-digit code to `{email}`. It expires in 10 minutes." 6-box OTP input
(§2.2) centered, auto-submits on completion. Beneath: countdown "Resend code in 0:48" (`body.sm`,
`ink.500`) that becomes a tappable ghost-link "Resend code" (`primary.700`) once it hits zero.

**Forgot Password / Reset Password** — Pattern A, two steps of the same visual shell: step 1 = email
field + "Send Reset Link" primary button; step 2 (post-link) = new password + confirm fields with
the same live-checklist pattern as Register, "Reset Password" primary button.

**Onboarding — Region Picker** — Pattern A, but full-screen (no back option except a skip that's
visually de-emphasized as a `body.sm` ghost link top-right, since skipping degrades every
downstream screen's relevance). `h1` "Where should we watch for you?" Two-level drill-down list
(Pattern B list rows): province list → tapping opens a district list (pushed, back-chevron
returns). Selected region gets a `status.safe` checkmark. Primary button "Continue" enabled once a
selection is made.

**Onboarding — Permission Primers** — Pattern A, one full-screen card per permission (Location,
Notifications, Camera — three sequential screens, swipeable or auto-advancing on decision), each:
large duotone icon representing the permission, `h1` headline explaining *why* in plain language
("We use your location to warn you before floodwater reaches you — only ever while the app is
open, unless you turn on live sharing with your safety group"), primary button "Allow," ghost
"Not now" beneath. This screen exists specifically so the OS permission dialog never appears
cold/unexplained.

### 4.2 Home

**Home** — Pattern G. 
- **Header zone**: brand-gradient block (matches Login's header treatment for visual continuity),
  `radius.lg` bottom corners, containing: `overline` "Good evening" (time-aware greeting), `h1`
  "Hello, {first name}" in white, location pin icon + region name (`body.sm`, white/80% opacity),
  notification bell icon top-right (white, with a small `status.critical` dot-badge showing unread
  count, tapping opens a notifications list sheet).
- **Alert banner** (§2.11, conditional): directly below header, only rendered when there's an
  active alert for the user's region.
- **Section: Quick Actions**: `overline` "QUICK ACTIONS," 2×2 grid of Chip-input-styled cards
  (§2.2) — Report Incident (category-neutral warning-triangle icon, `primary.500`), Request Help
  (hand-heart icon, `status.critical` tint since it's help-seeking), Safe Routes (compass icon,
  `status.trust` tint), Nearby Shelters (house icon, `status.safe` tint) — each card's icon tint
  hints at its downstream context without fully color-coding the grid into status colors.
- **Section: Latest Community Reports**: `overline` "LATEST COMMUNITY REPORTS" + "View All"
  ghost-link right-aligned, 2–3 List-cards (§2.3), each with category chip, severity badge,
  credibility chip, upvote count.
- **Section: Nearby Aid Requests**: same header pattern, List-cards with urgency badge
  (`status.high`/`status.critical` for Urgent) shown first.
- **Section: Family Safety Status** (conditional — only during an active alert with an active
  safety group): full-width card, `status.safe` tinted background if all members checked in,
  avatar row of members with a small check/pending indicator per avatar, "View Details" ghost

### 4.3 Map

**Map** — Pattern E. Edge-to-edge Mapbox view. Floating search bar (rounded pill, `surface.raised`,
`elevation.2`, magnifying-glass leading icon, positioned top, safe-area aware) — "Search places,
roads, shelters…". Floating vertical control stack top-right: layers-toggle icon button (opens a
sheet listing Flood Heatmap / Shelters / Infrastructure / Community Reports / Missing Persons as
individually-toggleable switches, §2.2), legend `?` icon button, recenter-on-me icon button.
Bottom sheet, collapsed by default to a peeking handle + one line summary ("⚠ 2 flood zones, 1
road closure nearby"), expandable by drag to show: the same one-line summary as a header, then
three full-width buttons stacked — "Report Incident" (secondary), "Request Help" (secondary),
"Find Safe Route" (primary, full brand-gradient fill since it's the map's main conversion action).
Tapping any hazard polygon/shelter pin/incident pin opens a smaller, non-collapsed tooltip sheet
(severity/status, confidence %, last updated, "View Details" button) instead of the summary sheet.

**Shelter Detail** — Pattern C. Header photo placeholder (illustration if no real photo available,
never a broken-image state), `h1` shelter name, status badge (Open/Closed), capacity as a
horizontal bar (`current/total`, `status.safe`→`status.high` gradient fill as it approaches
capacity), certification badge (`status.trust` "Certified" or `status.caution` "Pending
Certification"), address + distance, pinned bottom button "Navigate Here" (primary).

### 4.4 Community

**Community Feed** — Pattern B. Search bar + filter icon in the top app bar row (not floating,
since this isn't a map). Segmented tabs beneath: Latest / Verified / Nearby / Q&A (Q&A tab renders
a centered "Coming soon" empty state — no backing feature yet, but the tab stays visible per the
approved information architecture rather than being silently cut). Feed of List-cards: avatar +
name + verified badge (if applicable) + timestamp, category chip, `h3` title, `body.md`
description (2-line clamp), image thumbnail if present (16:9, `radius.md`), footer row: upvote
button (thumb-up icon + count, fills `primary.50` when the user has voted) / downvote (thumb-down,
muted styling — deliberately less visually prominent than upvote to nudge toward constructive
engagement) / comment count, credibility chip right-aligned. Official NGO/admin posts get a
distinct card treatment: `status.trust`-tinted left border (4pt) and a locked/non-interactive vote
row replaced by a small "Official Update" label.

**Incident Detail** — Pattern C. Category chip + severity badge in header row, `h1` title,
reporter avatar/name/timestamp, full description, media carousel (swipeable, dot indicator),
location shown as a small embedded static map snippet (tap to open full Map centered there),
status timeline (Pending → Verified → Resolved, horizontal stepper, completed steps filled
`status.safe`, current step pulsing `primary.500`), large upvote/downvote buttons pinned above the
bottom safe area alongside a "Message" ghost button if a conversation thread exists for it.

**Report Incident** (modal) — Pattern D. Close (×) top-left, `h1` "Report Incident." Section 1:
category grid (Chip-input, §2.2) — Flooding / Landslide / Fire / Road Collapse / Cloudburst /
Missing Person / Medical Emergency / Other, 2 columns, icon+label per category-color from §1.2.5.
Section 2: Title text field. Section 3: Description textarea with live character counter against
the 20-char minimum (counter turns `status.safe` once satisfied). Section 4: media uploader
(§2.12). Section 5: location card — pin icon, "Current Location: {reverse-geocoded address}," a
"Change" ghost-link opens a map-picker sheet. Footer (pinned): `body.sm` warning text in
`status.caution` — "False reports may result in reduced credibility score" (verbatim SDS copy) —
directly above the primary "Submit Report" button.

### 4.5 Resources — tab shell

**Resources** (tab root) — Pattern B shell with an internal segmented control at the very top
(Local Resources / Aid / Campaigns / Missing Persons) — one shared screen frame, four bodies.

#### 4.5.1 Local Resources

Category filter as a horizontally-scrolling chip row (not a segmented control here — five+
options don't fit a segmented pill) — Pharmacy / Fuel / Grocery / ATMs / Water, each a small pill
chip, selected = `primary.500` fill. List-cards: name, distance (`body.sm`, right-aligned),
open/closed badge (`status.safe`/`status.critical` — this is the one place `status.critical` is
used for a non-emergency "closed" state, acceptable since "closed pharmacy during a flood" is
genuinely high-stakes information, not a cosmetic status), verified checkmark if reported <6h ago,
"last updated Xh ago" caption, two small footer buttons: "Navigate" (secondary, `sm`) and
"Mark as Closed"/"Mark as Open" (ghost, `sm`, toggles based on current state).

#### 4.5.2 Aid

**Aid Requests list**: toggle chip row "All / Mine" top of list. List-cards: resource-type icon
(matching Request Help's category icons), title, urgency badge (Low/Medium/Urgent →
`status.safe`/`status.caution`/`status.critical`), status badge, distance, timestamp. Floating
"Request Help" primary button pinned bottom.

**Request Help** (modal) — Pattern D. Section 1: resource-type grid (Food/Water/Medicine/Clothing/
Rescue/Shelter — Chip-input, 3 columns given 6 short-label options). Section 2: title + quantity/
amount text field. Section 3: description textarea (20-char minimum, same counter pattern).
Section 4: media uploader (optional, max 3). Section 5: delivery location card (same pattern as
Report Incident). Section 6: urgency segmented control (Low/Medium/Urgent), selected segment
tinted with the matching status color rather than generic `primary.500` — the one segmented
control in the app that breaks from brand-color selection styling, intentionally, since the
choice itself *is* a severity signal. Footer: `body.sm` "Your request will be visible to verified
donors and NGOs in your area" above pinned "Submit Request" button.

**Aid Request Detail** — Pattern C. Icon+title header, urgency + status badges, description,
quantity, delivery location snippet, timeline (Pending→Assigned→In-Progress→Fulfilled, same
stepper component as Incident Detail), pinned footer: "Message" secondary button + (only if the
viewer is the requester and status is cancellable) "Cancel Request" danger-outline button.

#### 4.5.3 Campaigns / Donations

**Campaigns list**: List-cards with a category chip (Food/Medical/Shelter/etc.), title,
description snippet, linear progress bar (§2.13) showing raised/goal, region + "ends in Xd"
caption. Floating "Create Campaign" primary button pinned bottom (secondary priority action, so
this could also live as a top-right icon button instead if the screen feels crowded — designer's
call at high-fidelity stage).

**Campaign Detail**: hero image/illustration, `h1` title, large progress bar with raised/goal
numbers as `h2`, description, contributions list (recent donors, amounts, "Pledged" status chips),
pinned bottom "Donate" primary button opening an inline expand (not a new screen) with amount
entry (numeric keypad-styled input, PKR prefix) and "Confirm Contribution" button — matches the
old build's in-place expansion pattern rather than a navigation push, since donation is meant to
feel like one continuous low-friction action.

**Donation History**: simple Pattern B list, one row per contribution — campaign name, amount,
date, status chip.

#### 4.5.4 Missing Persons

**Missing Persons list**: List-cards with person's photo/avatar, name, age/gender caption, status
badge (Missing = `status.critical` tint, Found = `status.safe`), last-seen location + time,
sighting count. Floating "Report Missing" primary button (uses `status.critical`-adjacent iconography
given the content's gravity, but button itself stays `primary.500` for consistency with every
other "create" action in the app — severity color is reserved for status badges, not for every
button that touches a serious topic).

**Missing Person Detail**: large circular photo, name/age/gender header, status badge, description,
last-seen card (location snippet + time), reporter contact card (name/phone, tap-to-call icon),
embedded small map showing sighting pins connected by a faint dotted path (movement pattern),
sightings list beneath (chronological, each with location/time/reporter), pinned bottom "Report
Sighting" primary button.

**Report Missing Person** (modal) — Pattern D. Name, age (optional numeric), gender (segmented:
Male/Female/Other — matches old build), description textarea, last-seen location card, your
contact name + phone fields, media uploader (photo of the person). Submit button disabled until
all required fields + a resolved location are present.

**Report Sighting** (small modal/sheet, not full Pattern D): "What did you see?" textarea,
optional location override (defaults to current location), "Submit Sighting" primary button —
deliberately lighter-weight than the full report flow since this is meant to be fast.

### 4.6 Safe Navigation

**Safe Route Navigation** — Pattern E variant. Top: origin field (pre-filled "Current Location,"
editable) and destination field stacked in one card, `primary.500` "Calculate Safe Route" button
beneath. Below: "Quick Destinations" list (Pattern-B-style rows, not cards) — Nearest Emergency
Shelter / Main Hospital, each with a distance caption and chevron. Once a route is calculated, the
screen transitions to a full map view (Pattern E) with the route polyline drawn in `primary.500`
with `status.critical`/`status.high` colored segments overlaid anywhere the route crosses a
caution zone (a route should never look uniformly "safe blue" if part of it isn't), a persistent
bottom card showing ETA + distance + "Reroute" ghost button, and a toast that fires ("Route
updated — new hazard detected") if a live reroute occurs mid-navigation.

### 4.7 Safety Groups (under Profile)

**Safety Groups list** — Pattern B, simple rows (§2.7): group name, member count caption, chevron.
Floating "+" FAB (small, `primary.500`, bottom-right) to create a group — a secondary FAB distinct
from the global chatbot FAB, only present on this screen, positioned to avoid overlap (chatbot FAB
shifts up when a screen-local FAB is also present, or this screen's create-action moves to a
top-right icon button instead — flag for high-fidelity review to avoid two FABs stacking).

**Safety Group Detail** — Pattern C. Member list (avatar, name, email/phone caption, live-location
toggle switch trailing — green pin icon + "Sharing" label when on), "+  Invite Member" ghost row
at the bottom of the list, remove (×) icon per member (own-created groups only).

### 4.8 Alerts

**Alert Takeover** — Pattern H. No back button — dismissal only via explicit "I'm Safe" response
or a small "View on Map instead" ghost link that routes to Map with the hazard pre-focused (not a
generic close). Layout: large pulsing severity icon (Phosphor `warning`, `status.critical` fill,
gentle opacity pulse animation — the one deliberately "alive-feeling" animation in the whole app,
because it needs to visually compete for attention), `h1` alert title, `body.lg` message, "Safe
Routes" card (embedded mini-map + "Open Full Navigation" button), "Nearby Shelters" horizontal
scroll of compact shelter cards, "Emergency Contacts" list (safety group members, tap-to-call).
Bottom-pinned: two large side-by-side buttons — "I'm Safe" (`status.safe` solid, left) / "I Need
Help" (`status.critical` solid, right) — equal width, equal visual weight; this is the one screen
in the entire app where two primary-weight buttons appear side by side, justified because the
decision genuinely is binary and time-sensitive.

### 4.9 Chat & Calls

**AI Chatbot** — Pattern F. Top app bar shows a small bot avatar (brand-gradient circle with a
sparkle/chat-bot Phosphor glyph) + "LittleLife Assistant" + an online-status dot. Suggested-prompt
chips ("Report an incident," "Find nearest shelter," "Is it safe to go outside?") shown above the
composer on first open, disappearing once a conversation starts. Bot messages get a small
`status.trust`-tinted "AI" tag beneath the bubble to keep it clearly distinguished from a human
NGO responder in the same-styled thread pattern used elsewhere.

**Aid/Missing-Person Message Thread** — Pattern F. Header shows the linked resource's title as a
tappable chip beneath the participant name ("Re: Clean Water Needed →") that jumps back to that
Aid Request/Missing Person detail screen. Shared-incident messages render as an inline mini-card
(category chip + title + thumbnail) inside the bubble rather than plain text.

**Voice/Group Call (in-call)** — full-screen, dark (`ink.900` background regardless of light/dark
app setting — calls are always dark-chrome, matching platform convention), centered avatar(s) +
name(s), call duration timer, bottom control row: mute (toggle), speaker (toggle), end-call
(circular, `status.critical` fill, larger than the other two). Group calls show a grid of
participant avatars instead of one centered avatar.

**Incoming call** — full-screen overlay, caller avatar + name, "Voice Call" caption, two large
circular buttons: decline (`status.critical`, left) / accept (`status.safe`, right) — mirrors the
platform-native incoming-call convention users already know.

### 4.10 Profile & Settings

**Profile** — Pattern G. Header card: avatar, name, location, verified badge + "Level N" chip
(gamification level, client-derived), credibility ring (§2.13, small version) inline. Stat-tile
row (2×2 or 1×4, Reports/Donations/Assists/Points — §2.3 stat card variant). "Badges &
Achievements" horizontal scroll of small badge tiles (icon + label, greyed-out/desaturated for
unearned badges, full-color for earned — client-computed per the implementation plan's Gap 4).
"Recent Activity" list (max 10, each row: icon + description + relative time + point delta chip
in `status.safe`/`status.critical` depending on sign), "View Full History" ghost link. "Quick
Links" list block: My Reports / Donation History / Family Group / Settings — Pattern-B-style rows
with chevrons.

**Edit Profile** — Pattern A-ish single form: avatar (tap to change, camera-badge overlay icon),
name field, phone field, email field (read-only if verified, shown with a lock icon).

**Alert Preferences** — Pattern B rows-as-toggles: Email/SMS/WhatsApp/Push/Voice-Call switches,
minimum-severity picker (segmented: Advisory/Watch/Warning/Critical), language picker
(English/اردو — the Urdu label itself set in Noto Sans Arabic even while the rest of the screen is
in the active locale, so the option is always legible regardless of current language).

**Account Settings** — Pattern B rows: "Log Out" (plain row), a visually-separated "Danger Zone"
section (`overline` in `status.critical`) containing "Deactivate Account" (row, `status.caution`
leading icon) and "Delete Account" (row, `status.critical` leading icon) — delete opens a
password-confirmation Pattern-A sub-screen rather than a bare native alert dialog, given it's
irreversible.

**Credibility** — Pattern C. Large ring progress (§2.13) with percentage + point total centered.
Beneath: itemized history list, each row an icon (up-arrow `status.safe` for positive, down-arrow
`status.critical` for negative) + description ("Verified Report," "Inaccurate Report") + relative
time + point delta chip.

**Activity Timeline** — Pattern B, full-history version of Profile's Recent Activity list, with a
type filter chip row (All/Reports/Donations/Aid/Votes) at the top.

**My NGO** — Pattern B/A hybrid, reachable from Profile's Quick Links block. **Added here after
`WEB_DESIGN_PLAN.md`'s FE-coverage audit caught it missing from this doc's original screen
inventory** — any logged-in citizen can self-register an NGO (M1 FE-7's citizen half), which the
first pass of this plan never gave a screen. Status card at top: `SeverityBadge`-styled pill
showing "No NGO" / "Pending Approval" (`status.caution`) / "Active" (`status.safe`), with a
"Register an NGO" primary button shown only in the "No NGO" state, opening a short form (name,
contact email, contact phone) — a real backend gap applies here too: there's no route for a
citizen to poll their own registration's status after submitting, only the admin-facing approve/
reject routes exist, so "Pending" is inferred client-side from "a registration was submitted,"
not from a live status check, until backend adds one.

**Volunteer Invitations** — Pattern B, reachable from Profile's Quick Links block, also badge-
counted on the Profile tab icon when ≥1 invitation is pending and reachable directly from a push
notification tap. **Added for the same reason as My NGO above** — an NGO inviting an existing
citizen to volunteer (M1 FE-9's citizen half) needs somewhere for that citizen to respond. List
rows: NGO name + logo/avatar, invited-by name, date, two inline buttons — Accept (primary) /
Decline (ghost) — accepting promotes the account server-side and immediately signs the user out of
this app on their next token refresh (same `ErrWrongAppForRole` behavior as §3.2 describes for an
approved NGO founder), so the Accept action should show a brief explanatory toast before that
happens, not just silently boot the user.

**Offline Maps** — Pattern B rows: one per region, showing download-state (Not Downloaded /
Downloading with inline progress bar / Downloaded with size + "map data is Nd old" caption +
Update/Remove ghost actions).

## 7. Handoff checklist (for Claude Design / design execution)

- [ ] Build the token set in §1 as actual design-tool variables/styles before touching any screen
      — every color/space/radius/type reference in §2–5 should resolve to a token, never a
      one-off hex/px value.
- [ ] Build §2's component library as reusable components with the states listed (default/pressed/
      disabled/loading/error) before assembling any screen frame.
- [ ] Run a color-blindness simulation pass (deuteranopia + protanopia) specifically on §1.2.4's
      status-color set and §1.2.5's category palette — confirmed mutually distinguishable is a
      hard requirement, not a nice-to-have, given what these colors communicate.
- [ ] Contrast-check every text/background pairing introduced at high-fidelity beyond what's
      pre-checked in §1.2.1/§1.8.
- [ ] Design both LTR (English) and one full RTL (Urdu) screen for at least one of each pattern in
      §3, to catch mirroring issues (icon direction, text alignment, form field order) before
      applying RTL to all 50 screens.
- [ ] Light mode is the primary deliverable; dark mode (§1.2.7 token mapping) is a fast-follow
      pass applied after every light-mode screen is approved, not built in parallel.
